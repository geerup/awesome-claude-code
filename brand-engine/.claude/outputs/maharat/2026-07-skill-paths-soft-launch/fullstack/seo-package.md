## 3. Technical SEO findings

Format: finding, impact, recommended fix, owner.

---

### Finding T-1: Hreflang implementation for Arabic and English

Issue: The early-access landing page exists in two language versions (AR and EN). Without
correct hreflang tags, Google will either index the wrong language version for a given
search locale or show the English page to Arabic searchers in Saudi Arabia and the GCC.
This is the highest-impact technical finding for this campaign.

Impact: High. Organic traffic mismatch by language and locale. Lost Arabic-language
ranking signal. Incorrect landing experience for the target audience.

Recommended fix:
Implement hreflang link tags on both the AR and EN pages, in the HTML head and in the
XML sitemap (both locations for robustness):

On the Arabic page (maharat.com/ar/skill-paths/early-access):
  <link rel="alternate" hreflang="ar-SA" href="https://maharat.com/ar/skill-paths/early-access" />
  <link rel="alternate" hreflang="en" href="https://maharat.com/en/skill-paths/early-access" />
  <link rel="alternate" hreflang="x-default" href="https://maharat.com/ar/skill-paths/early-access" />

On the English page (maharat.com/en/skill-paths/early-access):
  <link rel="alternate" hreflang="ar-SA" href="https://maharat.com/ar/skill-paths/early-access" />
  <link rel="alternate" hreflang="en" href="https://maharat.com/en/skill-paths/early-access" />
  <link rel="alternate" hreflang="x-default" href="https://maharat.com/ar/skill-paths/early-access" />

Notes:
- x-default points to the Arabic version as the primary (Arabic-first brand rule).
- If there are additional GCC-locale variants (e.g., ar-AE, ar-KW), add them with their
  own hreflang tags. For this launch, ar-SA is the primary locale.
- Hreflang tags must be reciprocal: each page lists both itself and its counterpart.
- Confirm the exact final URL structure with conversion-engineer before implementation.
- If the site uses a sitemap for hreflang, replicate the same tag pairs there.

Owner: conversion-engineer.

### Finding T-2: RTL correctness on the Arabic landing page

Issue: Arabic pages require correct RTL rendering at the HTML root level and within every
mixed-direction content block (Arabic text adjacent to Western numerals, brand name in
Latin script, App Store badges, icon+text combos). Common failure modes: dir attribute
missing from the html element, inline elements defaulting to LTR, numerals or Latin brand
strings breaking the visual flow of an Arabic sentence.

Impact: High. A broken RTL page damages trust with Arabic-speaking users, reduces time on
page, and increases bounce rate, which is a negative ranking signal.

Recommended fix:
- Set dir="rtl" and lang="ar" on the root html element of the Arabic page.
- Do not rely solely on CSS text-direction; the HTML attribute is required for correct
  bidi algorithm behavior.
- Western numerals within Arabic text should use the Unicode bidirectional neutral
  characters correctly. Do not insert LTR override characters unless a specific numeral
  string requires it.
- App Store and Google Play badges (typically LTR assets) should be placed in a
  wrapper with explicit dir="ltr" so they do not disrupt the surrounding Arabic flow.
- Mixed-direction strings (e.g., "مهارات App") require bidi testing. Confirm with
  design-qa on the rendered output.
- Test on a mobile viewport (iOS Safari and Android Chrome) since RTL issues are more
  common on mobile rendering engines.
- Brand name "مهارات" in Arabic does not require special treatment; Latin "Maharat"
  inline within Arabic sentences should be wrapped in a span with dir="ltr".

Owner: conversion-engineer, design-qa to verify rendered output.

### Finding T-3: Crawlability and indexation timing for a soft launch

Issue: A soft launch requires deliberate control over when and which pages Google indexes.
Common risks: the page is published but blocked in robots.txt or with a noindex meta tag
during staging and that setting is not removed at launch. Or the inverse: the page is
indexed prematurely during staging, before it is ready, generating thin-content signals.

Impact: High. Premature indexation of a staging or placeholder page creates thin-content
and duplicate-content signals that can delay ranking of the final page.

Recommended fix (staged approach for a soft launch):
1. Staging and pre-launch (before 2026-07-01): disallow the landing page path in robots.txt
   for any staging or preview domain. Set meta noindex on the page in staging. Do not submit
   the URL to Search Console during this phase.
2. Launch day (2026-07-01): remove robots.txt disallow for the production domain path.
   Remove the noindex meta tag. Ensure the canonical tag is correctly set and self-referential.
3. Post-launch (first 48 hours): submit the URL directly via Google Search Console URL
   Inspection tool (requires Search Console access, open item below). This requests
   priority crawling.
4. Do not set a noindex tag as a "soft launch precaution" on the live page. Once the page
   is intentionally in market, index it intentionally. Noindex on the live page wastes the
   campaign's organic window.
5. For supporting content pages in the content briefs: these can be published and indexed
   as soon as they are ready; they are supporting organic, not gated. Recommend publishing
   content pages before or on 2026-07-01 to give them crawl time within the flight.

Owner: conversion-engineer with sign-off from Ahmed before the robots.txt or canonical
change goes live on production.

### Finding T-4: XML sitemap inclusion

Issue: If the maharat.com XML sitemap does not include the Arabic and English early-access
landing page URLs (and the hreflang pairs), Google's discovery of the pages may be slower
than needed within the 14-day flight.

Impact: Medium. Within a 14-day organic window, crawl delay matters. A sitemap entry
accelerates discovery.

Recommended fix:
- Add both URLs (AR and EN) to the XML sitemap with hreflang annotations (using the
  xhtml:link format within the sitemap for the language pair).
- Set the changefreq to "daily" for the flight duration to signal active content.
- Set the priority to 0.9 for the landing page URLs, and 0.7 for supporting content pages.
- Submit the updated sitemap to Google Search Console after launch.
- Arabic and English URL entries should both appear in the same sitemap or in linked
  sub-sitemaps, not in separate undiscoverable files.

Sample sitemap entry format (for conversion-engineer):
  <url>
    <loc>https://maharat.com/ar/skill-paths/early-access</loc>
    <xhtml:link rel="alternate" hreflang="ar-SA"
      href="https://maharat.com/ar/skill-paths/early-access"/>
    <xhtml:link rel="alternate" hreflang="en"
      href="https://maharat.com/en/skill-paths/early-access"/>
  </url>

Owner: conversion-engineer.

### Finding T-5: Page speed and Core Web Vitals baseline

Issue: No live page speed data is available (Search Console and CWV data access are open
items). However, common causes of CWV regressions on Arabic landing pages should be
pre-empted in the build.

Impact: Medium. Core Web Vitals are a confirmed Google ranking factor. A slow Arabic page
also directly harms conversion, particularly on mobile in Saudi Arabia where 4G/LTE is the
dominant connection type.

Recommended fix (pre-emptive, for conversion-engineer):
- LCP (Largest Contentful Paint): the hero image or headline should be the LCP element.
  Pre-load the hero asset. If the hero uses a brand illustration or product screenshot,
  use a WebP format with a width-appropriate srcset. Target LCP under 2.5 seconds.
- CLS (Cumulative Layout Shift): reserve space for the hero image in CSS before it loads.
  Arabic web fonts (if custom) must use font-display: swap or optional to prevent layout
  shift. Target CLS under 0.1.
- FID/INP (Interaction to Next Paint): minimize JavaScript execution in the first load.
  Gate/signup form scripts should load after the main content is interactive.
- RTL layouts are occasionally slower due to CSS recalculation if direction is applied
  late. Apply dir="rtl" in the HTML, not via JavaScript at DOMContentLoaded.
- Compress and lazy-load any below-fold images. Do not lazy-load the LCP hero.

Owner: conversion-engineer. Validated after build with PageSpeed Insights or Lighthouse.

---

### Finding T-6: Canonical and duplicate-content risk

Issue: Early-access landing pages sometimes exist in multiple states: a teaser/holding
page, the full page, a campaign-URL variant with UTM parameters. UTM parameters and
session tokens in URLs can generate near-duplicate pages in Google's index.

Impact: Medium. Duplicate indexation dilutes ranking signal across URL variants.

Recommended fix:
- Ensure the canonical tag is set on the page itself, pointing to the clean URL without
  UTM parameters.
- UTM parameters should be blocked from indexation via Google Search Console's URL
  parameter settings (requires Search Console access, open item).
- Do not use separate URLs for A/B test variants if those variants will be indexed. Use
  server-side testing or noindex on variant URLs.
- If the teaser/holding page predates the full launch page, replace it in-place at the
  same URL rather than publishing a new URL. This preserves any crawl equity the teaser
  may have accumulated.

Owner: conversion-engineer.

---

### Finding T-7: Open Graph and social crawlability

Issue: Social platforms (Meta, Twitter, WhatsApp link previews) fetch the page's Open
Graph tags. Incorrect or missing OG tags reduce the quality of organic shares and paid
social previews, and WhatsApp link previews (relevant to the gate platform, open item)
use these tags directly.

Impact: Medium for organic SEO, high for the campaign's social and WhatsApp gate
experience.

Recommended fix:
- Implement og:title, og:description, og:image, og:locale, og:url on both AR and EN pages.
- og:locale: ar_SA for Arabic, en_US or en_SA for English.
- og:image: a brand-constant, text-free image per the creative direction (no Arabic text
  baked into the image, per the brief). Minimum 1200 x 630px. Confirm asset availability
  (open item: approved imagery).
- og:title and og:description should match the on-page title and meta, or a social-
  specific copy variant (copywriter-ar or copywriter-en fills this slot).
- WhatsApp unfurls og:image at a 1.91:1 ratio. Ensure the hero image is sized and cropped
  accordingly so the brand mark is visible in the preview crop.

Owner: conversion-engineer (implementation), copywriter-ar and copywriter-en (slot fill).
